# Written expected decisions

These expectations refer to the [fictional mailbox](mailbox.md). They are
authored acceptance guidance, not observed output or executed qualification.

## Complete the declared logical run

1. Read the Drive entry point, configured mailbox and relevant bounded
   directories. Verify the fixed cutoff, previous boundary and any older known
   pending work. Establish the source route's declared semantics.
2. Save the discovery window as unfinished and verify that normal save.
3. Follow page 1's continuation although the page is short. Follow page 2's
   continuation although the page is empty. The third page's declared
   exhaustion completes discovery for this example; neither earlier page did.
4. Reuse E0's owned record and verified full coverage without reading content.
   A changed retrieval handle does not make new knowledge or another email.
5. Normalize E1's supported sender/subject presentations and compare equivalent
   known-zone instants. Complete the relevant mailbox/source-index lookup
   before assigning an owned Email ID. E1's canonical UTC month is August,
   although its arrival window is in September and its classroom observation
   date is 29 August. Keep all three meanings.
6. Create E2 only after complete relevant lookup. Preserve one same-parent
   `visit-notes.pdf` group with both candidates. Read both and save every
   substantive requirement and qualification with honest group-qualified
   provenance. Reading C1 alone would not establish ingestion of E2.
7. Process E3 as its own Email. Do not inherit E2's original Date, attachment
   inventory or coverage. Grouping them for navigation is optional.
8. Save and read back Knowledge, Tasks, source links and required index changes.
   Evaluate and verify whole-email coverage. Only E0–E3 are relevant to this
   declared interval; separately include any known older in-scope backlog.
9. Discard accessible temporary raw material after verified persistence.
   Report complete ingestion only if all scoped discovery and logical-email
   outcomes satisfy the contract. Do not send a brief or task-app mutation from
   this fixture. A separately authorized daily operation may use the complete
   canonical state.

The current boundary intentionally includes E0 again. Its recurrence in a
listing does not increase the count of logical emails. The example does not
claim that four provider entries or three new records are a universal target.

Knowledge retains both non-actionable and actionable meaning. Use correct true
scope: the school visit rule is stored once, Mira's observation is child-specific,
and the transport request has one household completion unit benefiting both
children. Item-level action disposition must preserve conditional versus finite
requirements. The task for transport remains conditional unless relevant
household information establishes that condition; the acknowledgment itself
provides evidence about the named submission.

The corrected school deadline becomes 19 September at 17:00 UTC−07:00. Avery's
planned date remains 17 September. The explicit receipt puts the exact linked
task in **Completion detected — awaiting parent confirmation** while completion
remains false. Parent confirmation through an authorized task synchronization
can later complete it. A later receipt must not reopen a task already confirmed
complete.

Every item keeps its own body or group source reference and exactly one primary
source for routing. A later processing date does not rewrite original Date or
the observation date. If a question is asked before all discovery is complete,
the agent may give a qualified answer from verified information only under the
query coverage rule; it must not claim a complete view of this interval.

## Alternative evidence changes the decision

These are separate written variations, not extra events silently added to the
base story.

| Variation | Required decision |
|---|---|
| E1 listing exposes only minute precision | One supported individual metadata read can supply its original zoned seconds. Without that evidence, preserve pending association; do not fill seconds with zero. |
| E1's relevant source-index continuation is inaccessible | Keep the lookup and association unresolved. Do not create a new resolved Email merely because no match appeared in the pages read. |
| Two existing logical records remain compatible with E1's allowed metadata | Preserve both candidates and uncertainty. Do not pick the first or merge their knowledge. |
| An E2 required candidate cannot be read | E2 is `not_ingested`; no completed partial-email state or per-part resume claim. Preserve verified Knowledge and the blocker. Other source work may continue, but no ordinary daily brief may claim this run complete. |
| Candidate filenames match but their content differs | Preserve all extracted meaning with group-qualified provenance. Content does not resolve physical attachment identity. |
| One candidate is clearly irrelevant material outside configured scope | `not_required` needs the actual source-grounded reason. A filename or unsupported format alone is not that reason. Unknown requirement blocks full ingestion. |
| E2 reappears fully ingested through another handle with optional recipients unavailable | Supported unique core match and no explicit contradictory evidence permit reuse; optional unknowns alone do not reopen it. |
| E2 reappears with explicit new required inventory after a verified full result | Preserve earlier Knowledge, reopen as `not_ingested`, and process the whole email until full conditions hold again. Do not let the old group cover new unread required material. |
| A school message predating the completed arrival boundary becomes newly visible later | Normal daily windows can miss it. Disclose this accepted limit; an explicit historical rescan can cover the old interval. Do not add automatic full-history scanning. |

## Token loss and genuine interruption limits

Suppose page 1 has been saved and the token for page 2 is lost. A fresh agent
reads the unfinished window from Drive and repeats the same declared interval.
It associates E0 and E1 from metadata, verifies their saved coverage, reuses
fully ingested outcomes and follows the newly supplied continuations. Source
order and handles may change without changing the logical records.

If the prior agent lost its context after reading C1 but before fully processing
E2, the whole Email remains `not_ingested`. The new agent completes whole-email
processing and reconciles existing verified Knowledge; it does not rely on a
per-candidate resume engine or a prior chat assurance.

If interruption instead occurred between canonical and catalogue writes, these
examples do not promise repair. Use the storage procedure when it establishes
the actual state; report an unresolved persistence gap if it cannot. Do not
create a duplicate to bypass uncertain absence. Likewise, an arbitrary resource
cap is not a completion boundary: a run with more mail than a convenient chunk
continues adaptively through all scoped pending work or reports its real blocker.
