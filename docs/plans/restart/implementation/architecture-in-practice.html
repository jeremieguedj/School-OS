How School-OS works

This explains the design, not a finished or tested product. The minimal Python helpers and new setup, shared-adapter, completion-review and brief-recipe instructions are written; the full MVP is still being implemented. All walkthroughs below are written examples. They do not run agents, process email or send anything.

We use GPT Work as the main agent and Gemini Spark as a second agent, as requested. Each example assumes the necessary authorized tools are available. Their names do not establish compatibility.

The big picture

Five layers, with one agent doing the work

Code handles small mechanical steps

The authored Python helper normalizes a subject, normalizes already-extracted address parts and measures UTF-8 text size. Recipes point to the actual script. It does not decide what the school meant or operate your accounts.

The agent handles the operation

It interprets content, makes source-supported connections, saves and checks results, and uses its own batching and continuity. School-OS does not manage a queue of agents or scheduled jobs.

Approved setup and adapter design

One tool adapter; each agent brings its own connector

The adapter explains what an operation means in the tool. The connector provides how this agent performs it. A reusable adapter contains no agent-specific API calls, SDK code or credentials.

Shared adapter describesAgent’s connector handles
Which tool concept holds parent completion, planned date and the School-OS task reference.Which exposed operation reads or changes that concept, with the connector’s actual arguments.
What a complete task listing or successful readback must establish.API calls, pagination mechanics, transport and the actual returned evidence.
Which distinctions the tool cannot represent and how to report that limitation.Current permissions, missing operations, connection failures and connector-specific limits.

If the adapter is missing: the setup agent can author the tool-level mapping, save the user-created addition in extensions and make it findable through the instance’s existing instructions/configuration. Another agent reuses it. If the connector lacks a required operation, writing an adapter cannot manufacture access.

Supplied adapters live with official system material; household additions live in extensions. The parent’s selected tool/account and relevant choices belong in instance. Credentials stay with the connector. This adds no central tool registry or automatic adapter marketplace.

Reusable instructions are now authored: setup interview, create or reuse a tool adapter, and adapter writing template. No concrete tool mapping or connection has been tested.

Shared memory

Drive holds many small files, not one giant JSON

Information in the instanceWhat it tells the next agent
ConfigurationWhich school/child and mailbox scope matter; applicable timezone and your selected task/output preferences.
Knowledge and source linksWhat the school said, including exceptions, dates and corrections, and where each statement came from.
Tasks and parent stateWhat action is required; its school deadline; your separate owner and plan; detected completion awaiting review versus parent-confirmed completion, with evidence.
Source and attachment indexWhich logical email or reply was identified, its original metadata, and the attachment candidates belonging to it.
Discovery and content coverageWhich search windows were fully listed, which remain unfinished, and which bodies and attachments were actually processed and saved.
Task synchronization informationWhich app entry represents a School-OS task and the last values verified on both sides.

These describe information roles, not a newly approved field schema or one file per row. The separate records-and-save framework is outside MVP.

Directories point to the relevant JSON pages, like a table of contents pointing to pages in a book. A page has a default limit of 64 KiB; a directory page has up to 100 entries and can point to another directory page. More pages can be added as history grows. Long substantive text is split without throwing it away.

There is no single-JSON limit on the whole history. Drive capacity and practical reading costs still matter. A question about one school event should load the relevant pages, not the entire school year.

Technical detail, without a whole-instance download

From a directory entry to a saved fact

A JSON page is a small file containing related records. A directory is a separate set of pages that tells the agent where to find those records. One email can lead to several knowledge claims and tasks; one data page can hold several records. There is no requirement to create one file per email.

What is inside a JSON data page?

D1 requires page-level information identifying the instance, record family, School-OS page ID and schema version. The records then carry the information appropriate to that family. A knowledge page contains knowledge; a task page contains task state. Stable School-OS references connect the pieces.

Reading sketch only: the field labels and identifiers below illustrate those approved meanings. They are not a newly adopted persisted schema, a generated instance or a template to execute. The concrete data representation and index rules are still open; see questions 1 and 2.

{
  "instance_id": "household-example",
  "family": "knowledge",
  "page_id": "knowledge-page-example",
  "schema_version": "illustrative-only",
  "records": [
    {
      "claim_id": "claim-lunch-example",
      "statement": "Bring a nut-free packed lunch.",
      "exception": "School-meal recipients receive a meal.",
      "applies_to": "Robin's museum visit",
      "source_email": "email-museum-example"
    }
  ]
}

Following source_email leads to the indexed logical email and its original metadata; it does not mean the raw email was copied into this page. A related task can reference that claim while keeping its own parent state. Correction relationships point to the supporting and superseded claims; the old statement is retained.

How are the right files found as history grows?

A directory entry identifies a target page by its School-OS ID and can include a current Drive access handle. Each directory page holds at most 100 entries and explicitly points onward when more pages exist. Agents follow those links as needed, rather than depending on remembered provider tokens or scanning every file at startup.

The topic/entity index is rebuildable navigation over canonical knowledge, not a second authority. It finds candidate claims; the agent reads the actual claims, their qualifications and relationships. A missing, stale or incompletely traversed index cannot prove that a fact does not exist. Source/month directories remain an approved lookup route.

Source routing uses the original sending instant’s UTC month, so equivalent timezone presentations reach the same partition. Missing or unclear dates remain discoverable pending observations; they are not silently replaced with today’s date. Work/output history, where retained, is routed by recording month. The deferred job registry and write-repair machinery are not introduced by these routes.

What happens when information is saved or a page fills up?

The agent reads the relevant current pages, preserves existing information and approved meanings, and prepares the needed changes. It uses its Drive connector to save the affected bounded pages and directory references, then reads back enough to establish the intended values actually saved. It does not rewrite the entire history.

A data page has the approved 64 KiB encoded-JSON default limit. More pages can be added. Long substantive text is split into ordered segments linked to the same claim, normally at paragraph boundaries; an oversized paragraph is segmented without deleting its content. The agent must retrieve all needed segments before claiming to have read the whole claim.

The authored utf8_size helper can measure the exact text to be stored; it does not decide how to split or save it. Resource handling and actual tool calls remain with the agent. These are normal save obligations, not an atomic multi-file transaction or an interrupted-write repair guarantee.

Why JSON rather than Markdown?

JSON gives agents explicit values and links to read and update: school deadline, parent plan, completion, source reference and coverage stay distinct. Markdown is easier for people to write and read, especially for long explanations. It can also carry structure, but needs equally consistent conventions for updates and references.

Current D1 selects JSON for canonical structured data. Human-readable recipes and shared tool adapters can be written as documents; they are instructions, not the household’s structured knowledge. A Markdown/JSON knowledge hybrid is a possible alternative, not a change adopted here. Neither format alone guarantees correctness, good search or complete ingestion.

The essential distinction

How does an agent recognize an email it has seen before?

It compares allowed source metadata: the logical mailbox, original subject, sender, original sending Date and, when comparably available, received Date, To/Cc roles and attachment names/count. Originals and date meaning, timezone and precision are retained alongside comparison values. School-OS owns the logical record ID.

A provider's message ID is an access aid. A different ID does not prove a different logical email. Bodies, quoted replies, images, attachment bytes and hashes are never used for email identity or thread association.

Attachments belong to their parent email and original filename. Two files called “form.pdf” in different emails are separate parent-bound cases. Repeated names in one email remain a candidate group; the agent must preserve ambiguity and each candidate's actual read coverage.

A metadata match is not proof that new or unread material was processed. Prior verified coverage remains evidence only for what was established. The exact repeated-appearance policy and automatic Date sufficiency threshold still have open D4 choices.

If a temporary pagination token is lost, the agent can revisit the unfinished search window saved on Drive. That is different from repairing a half-written set of knowledge/task files: general interrupted-write repair is outside MVP.

Approved setup interviewScenario 1

Set up School-OS for the first time

“GPT Work, help me set up School-OS for Robin at Cedar School.”

Read / retrieve

Provided School-OS instructions; existing instance/configuration if present; current agent’s declared tool capabilities; any shared adapter.

Interpret / operate

Interview the parent. Match available tools to their choice. Create a missing tool-semantic mapping without API-specific code.

Save / update

Entry point and D1 areas for a new instance; household/source/tool choices; shared adapter and its reference. Import coverage only for an actually processed scope.

  1. Start with a short interview.

    GPT Work asks about the child/school, source mailbox and scope, timezone and desired outputs. It checks whether you already have an instance and reuses choices you have already made.

  2. Offer task-tool choices that this agent actually knows and can reach.

    It asks which task app you prefer and presents available options with relevant limits. For example: “I have an authorized route to Tool A. Tool B is known but not connected here. Which do you want to use?” These labels are fictional; no universal list is assumed.

  3. Find or create the selected tool’s shared adapter.

    If a mapping exists, read it. If the tool is accessible but the mapping is missing, author how its concepts represent School-OS task identity, parent fields and synchronization evidence. API calls and authentication stay with the connector. Unsupported meanings remain explicit.

  4. Establish the intended Drive instance.

    For a new instance, create the readable entry point and approved system/instance/extensions separation. For an existing instance, verify its identity and preserve its data and additions. Supplied instructions belong with system material; a new household adapter belongs in extensions.

  5. Save the interview’s choices and the adapter reference.

    Use the instance configuration for the selected tool/account, household/source scope and output choices. Keep the adapter findable through the existing entry point/configuration. Read back the saved choices and mapping. Do not put credentials into Drive.

  6. Agree what initial information to import.

    You might explicitly request school mail since September 1. Follow the ingestion flow below and save truthful discovery/content coverage. Creating the folders does not establish that mail has been ingested, and an import request does not automatically authorize a backlog email blast.

  7. Keep the entry point and arrange any jobs with your agent.

    Another agent starts from the same Drive instance, finds the same selected tool adapter and uses its own connector. Schedules belong to users and their agents; School-OS adds no central scheduler or adapter registry.

Expected outcome: your choices are recorded, the shared tool mapping is discoverable, and any requested import has honest coverage. A missing adapter can be created; a missing connector capability remains a limitation.

The setup recipe and adapter procedure are authored and unexecuted. A packaged installer and upgrade manager remain outside MVP.

Approved query behaviorScenario 2

Ask a fact question: the actual lookup flow

“Does Robin need a packed lunch for the museum trip?”

Read / retrieve

Entry point/configuration → topic or source/month directories → claim pages and relationships → source metadata and relevant coverage.

Interpret / operate

Apply the sourced rule to Robin, including exceptions and uncertainty. Fetch original content only if the answer needs missing or rechecked detail.

Save / update

Usually nothing. If authorized missing-source processing occurs, save the resulting information, source references and actual coverage before using it as verified.

  1. Read the entry point and relevant configuration.

    Using its Drive connector, the agent verifies the household instance and reads Robin’s school context and the query instructions. It loads the shared Drive tool mapping where needed; no previous chat is required.

  2. Turn the question into a focused lookup.

    Identify the child, event and topic: Robin, museum visit, lunch. Use the topic/entity directory to locate candidate knowledge pages. Follow required directory continuations. The source/month directory is another route; there is no full-history download at startup.

  3. Read the referenced knowledge pages.

    Check that the retrieved page declares the intended instance, family and School-OS page ID. Read the relevant claims and any needed long-text segments. The directory points to the information; it does not replace reading it.

  4. Follow the relationships and source references.

    Read applicable corrections, supporting evidence and conflicts. The source index supplies the original message metadata and any attachment location needed to explain provenance. A newer timestamp alone does not make a statement a correction.

  5. Read relevant discovery and content coverage.

    Check whether an unfinished search, unread reply or attachment could change this answer. No known gap in the portion read is not proof that all applicable coverage is complete. Do not declare unread material irrelevant merely because its subject does not say “lunch.”

  6. Apply the meaning to Robin.

    The claim says “Bring a nut-free packed lunch unless your child receives a school meal.” Check the relevant saved household information, if known. If Robin’s meal arrangement is unknown, preserve the condition instead of inventing the answer.

  7. If a necessary fact is missing, choose an honest branch.

    Within the request’s authorization and available capabilities, the agent may retrieve and process missing source material, save its information and coverage, and read it back. Otherwise it answers from verified information with the gap stated. A question does not require clearing every unrelated unfinished item.

  8. Respond with the fact, qualification and source.

    Use the verified claim and the established coverage. The ordinary complete-information path makes no canonical update merely to answer. A task or parent state is read only when the question needs it.

“The school asks for a nut-free packed lunch unless Robin receives a school meal. I do not yet know whether Robin does. The source is ‘Museum visit’, sent September 10.”

If relevant coverage is incomplete, say so. An inaccessible original prevents rechecking it but does not erase previously saved verified knowledge.

Approved D5Scenario 3

Change a task in your own task app

You change “Return vaccination form” to done in your task app.

Read / retrieve

Shared task-tool adapter; current app task through this agent’s connector; Drive task page including any pending confirmation; last values verified on both sides.

Interpret / operate

Match by School-OS task identity. Compare each current value with the shared baseline; accept an unconflicted parent change or surface a conflict.

Save / update

Affected canonical task page and any needed task-directory references; permitted app changes; verified shared values after readback. The school’s evidence is retained.

  1. Find the right School-OS task.

    The agent reads the shared adapter for the chosen task tool and uses its own connector to read the School-OS task ID carried in the mapped app field and verify the binding. A similar title is not enough.

  2. Read three versions.

    The agent reads the current Drive task, the current app task and the last values verified on both sides.

  3. Identify your edit.

    Previously both were open. Drive is still open; the app now says done. With no conflicting completion edit on Drive, this is an allowed parent change.

  4. Save the completion on Drive.

    Retain the parent completion and available evidence. Keep the school's original request and deadline: completing the task does not erase what was asked.

  5. Synchronize other unconflicted fields and verify.

    For example, an owner change in the app can coexist with a planned-date change on Drive. Check the resulting app and Drive values before treating them as the new shared baseline.

  6. Use the new state in later answers.

    The form is now completed in the canonical task view. Re-reading the original request or a routine reminder does not reopen it.

What if the two sides disagree?

Two different edits to the same field need review. For example, if the previously shared planned date was September 16, Drive now says September 17 and the app says September 18, neither silently wins. Other unconflicted fields remain usable.

A planned date is your household plan; it does not rewrite the school's deadline. Deleting the app task also does not mean the request is completed or cancelled. A missing task ID or unreadable app state leaves synchronization unresolved instead of guessing.

Yes—an explicit completion in the correctly linked task app can update Drive. A completion entered through School-OS can likewise update the app during a supported sync. If one side cannot be verified, the agent reports that limit rather than saying both are synchronized.

Approved directionScenario 4

A daily run ingests school emails

“Process all pending Cedar School mail through 06:00 today, including earlier material still unprocessed.”

Read / retrieve

Source scope and saved windows/coverage; shared mail/Drive mappings; mailbox listings; relevant individual metadata, bodies and attachment candidates.

Interpret / operate

Associate by source metadata. Extract full substantive meaning in the agent’s temporary workspace. Relate facts, corrections and genuine tasks.

Save / update

Affected source/knowledge/task pages and directory references; accurate discovery/body/attachment coverage. Verify saves, then release temporary raw copies.

The cutoff above is explicitly chosen for this fictional request. The product's default daily cutoff is still an open D4 decision.

  1. Read the scope and saved coverage.

    GPT Work checks the configured mailbox/school and completed or unfinished source windows. It uses School-OS processing evidence, not the mailbox's read/unread icon, to assess what is known.

  2. Finish discovery for the agreed scope.

    Follow every available continuation, even after a short page. Record unfinished windows honestly. A silently capped search or a result count cannot prove that all relevant mail was found.

  3. Identify each email and reply from metadata.

    Use the original Date with its meaning, timezone and precision, original subject, sender and other allowed metadata. Reuse an existing logical record only when the approved recipe supports it. Ambiguity stays visible; a thread is only a navigation aid.

  4. Read the actual body and attachments.

    Process the new departure-time correction, the vaccination-form message and the newsletter PDF separately. Unknown inventory or an unread same-name attachment candidate is still a gap. Content is read for meaning, never to establish email identity.

  5. Save substantive knowledge and tasks.

    Keep the revised departure time with its source and correction relationship; preserve any lunch exception; create or relate genuine action items. Keep parent plans and completion intact.

  6. Save accurate coverage and verify persistence.

    Check that the extracted information, source references and real processing state saved on Drive. Then discard accessible temporary raw copies. Originals stay in the mailbox.

  7. Continue until the entire agreed ingestion is complete.

    The agent chooses practical batches for its environment. A finished batch is progress, not permission to leave the daily task half done. It can synchronize tasks through the configured route; the approved daily starter discloses a task-app synchronization failure and can still use verified Drive information after complete ingestion.

  8. Only then compose the ordinary daily brief.

    Discovery, relevant body/attachment processing and saved results must support completeness. If an attachment cannot be read or the source cannot be completely listed, report the blocker and keep the task incomplete.

Expected outcome: all required information in the agreed scope is processed and saved before the daily brief. A correction near the end of the work must not be missed because an early batch already looked useful.

Still to settle: the default daily cutoff, some Date/association and repeated-appearance rules, and the exact search-time policies. The approved outcome is complete ingestion; this page does not invent those remaining defaults.

Approved: parent confirmationScenario 5

Detect completion, then let the parent confirm

Clear evidence moves the task into “Completion detected — awaiting parent confirmation.” It does not check the task off. The task stays separate and easy to review, using a supported status or section in your chosen task app.

Fictional school reply: “We have received Robin’s completed vaccination form. Nothing further is required.”

Read / retrieve

The reply and its own processing coverage; the related school request and task; current Drive/app parent state through the shared tool mapping.

Interpret / operate

Establish whether clear evidence satisfies this child’s specific obligation. Classify detected completion for parent review; never silently check it off.

Save / update

Source-linked evidence and pending-confirmation state on Drive. Show it in a supported task-tool status or section. After parent confirmation, sync completed state and verify both sides.

  1. Process the new reply as its own source.

    Identify it by approved metadata, read its body, and save its information and coverage. It does not inherit the original email’s processing flag.

  2. Check what it proves.

    Link the child, school, form and actual request. “We received your message” is not necessarily form acceptance; “page two is missing” does not satisfy the whole request. Receiving a form does not prove vaccination itself was completed.

  3. Record detected completion on Drive.

    For clear evidence satisfying the linked task, save “Completion detected — awaiting parent confirmation” with its source. Retain the school deadline and household notes. Keep an already confirmed task completed.

  4. Show the review state in the parent’s task tool.

    The shared adapter maps it to the tool’s supported status or section. GPT Work uses its own connector to apply and verify that mapping. The task stays uncompleted. If the route cannot represent the distinction, keep the state on Drive and report the app limitation.

  5. The parent reviews and checks tasks off.

    The parent can go through the separated group and mark the tasks they confirm as done. Until then, detected completion is not reported as parent-confirmed completion. If evidence is disputed or the parent does not confirm, do not complete the task.

  6. The next authorized sync records final completion.

    Read the current app task, canonical task and last verified shared values. Accept the unconflicted parent confirmation under D5, save it on Drive and verify the resulting state. Conflicting edits or unknown outcomes remain explicit.

Before confirmation: “The school confirmed receiving Robin’s form. This task is waiting for your confirmation.”

After the parent checks it off and synchronization succeeds: “You confirmed this task completed.” The source acknowledgment remains linked.

Marking a correctly linked task done directly in the app remains an approved parent action; it does not need to pass through detection first. A generic school reminder or source replay does not erase that confirmation.

Could this become fully automatic later?

Yes, after evidence about accuracy is available and a later explicit decision enables it. The current approval has no accuracy threshold, monitoring service or automatic switch to direct completion. Future automatic closure is separate from today’s parent-confirmation flow.

This change also does not expand source access: the agent uses evidence it is authorized to process. Discovering parent-sent mail or adding another mailbox remains a source-scope choice.

The reusable completion-review procedure is authored and unexecuted. Shared adapters describe the status/section mapping; each agent’s connector provides its own access mechanics.

Optional capability in scopeSome delivery choices openScenario 6

Generate an audio brief

“Read me today's school update as an audio brief.”

Read / retrieve

Relevant canonical knowledge/tasks/source links and coverage; requested brief settings; shared audio-tool adapter and this agent’s available connector.

Interpret / operate

Select and compose faithful narration, then have the authorized service generate audio. Preserve qualifications and verify the observed outcome.

Save / update

The generated audio is a derived output. Its Drive retention/location and delivery ordering are still unresolved; this scenario does not choose them.

  1. Check the request and available audio tools.

    The agent reads the selected audio tool’s shared adapter and identifies an authorized connector that can supply its required operations. Code execution alone does not supply an audio service or permission to use one.

  2. Check the daily ingestion gate.

    If this is the daily brief, finish and verify the agreed ingestion first. Audio cannot bypass an unread attachment or incomplete search.

  3. Prepare the selected brief text.

    Use saved, source-linked information and task state. Keep conditions and uncertainty: “bring lunch unless receiving a school meal” cannot become “everyone needs lunch.” Follow the chosen recipe. The starter daily template selects newly verified or corrected information plus relevant open tasks, shows original dates and discloses failed task-app sync. A household can choose another conformant recipe.

  4. Generate the audio.

    The agent uses the authorized service with the prepared narration and requested settings. Raw school attachments do not need to be uploaded as an audio-source archive.

  5. Check whether generation succeeded.

    If the response is uncertain, the agent checks the service's available job or artifact evidence. It does not invent success or blindly request a second generation.

  6. Deliver according to the selected policy.

    Retention on Drive and whether email goes before or together with audio still need decisions. Keep useful content/generator/sender attribution; do not imply a central job registry exists.

Expected outcome when supported: audio that reflects the same verified school information as the brief text, with an honestly established generation result. Unsupported or failed audio is reported as such.

Fresh-agent access approvedManual partial-brief policy openScenario 7

Ask a different agent to send a manual email brief

“Gemini Spark, here is my School-OS Drive entry point. Email me a new brief about the museum trip and its outstanding tasks.”

Read / retrieve

Drive entry point/configuration and recipes; the same selected shared tool adapters; relevant knowledge/task/source pages and coverage.

Interpret / operate

Gemini Spark uses its own authorized connectors, checks coverage and composes the requested new brief. It does not recreate GPT Work’s tool mappings.

Save / update

A new sent output through the chosen mail tool, with available generator/sender attribution. Any fresh processing or task sync saves its own verified changes; no central output registry is added.

  1. You provide access and authorize the outcome.

    The Drive pointer shows where to start; it does not grant permission by itself. Gemini Spark needs Drive read access and an authorized email-sending route. It also needs source or task-app access if the requested work requires fresh processing or synchronization.

  2. The new agent orients itself.

    Read START-HERE, verify the instance and load the relevant brief instructions/configuration and shared tool adapters. Gemini Spark uses those same mappings through its own connectors. It does not need GPT Work’s memory or a Gemini-specific adapter, and does not need to drain every unrelated unfinished task.

  3. Clarify what this new brief covers.

    Read the recipe you chose, such as your saved museum-trip brief, along with the stated event, reporting interval, recipient and output preferences. You and your agent may create another recipe if you want a different brief. A manual request is a new output, not automatically a repeat of the last scheduled send.

  4. Retrieve knowledge, tasks, sources and coverage.

    Read the relevant Drive pages. Existing verified facts can be used without mailbox access. Check whether missing processing could affect this brief and whether task-app edits have been synchronized.

  5. Resolve or disclose the limits.

    In the complete-coverage example, continue. If required information is missing, process it only with suitable authority and capability. Whether an explicitly limited manual email brief may be sent without complete coverage is still an open policy; the daily gate alone does not settle that.

  6. Compose and send through the authorized route.

    Keep source references, school deadlines, parent plans and completion distinct. Identify Gemini Spark as the generating agent and the actual sending account/service where available; they are not necessarily the same thing.

  7. Verify the send and report its outcome.

    If the send response is uncertain, use available authorized sent-message or delivery evidence. An empty or stale search is not proof of failure; do not blindly send again. Sent evidence does not prove that you received or read the message.

Expected outcome: the second capable agent can produce a fresh, source-linked brief from the same saved school information. It uses Drive continuity, not a handoff conversation with GPT Work.

What if the agent knows some relevant information is missing?

Example: the museum notice is saved on Drive, but today’s newsletter has not been processed. That newsletter might change the departure time. You ask Gemini Spark to email a trip brief now.

  1. Finish processing, then send. If authorized and capable, the agent reads the newsletter, saves any changes and verifies coverage. It can then send a brief based on the complete relevant information.
  2. You explicitly choose a limited brief. You say, “Send what you know now and tell me what is missing.” The proposed exception would allow an email that says, “Based on the processed museum notice. Today’s newsletter is not processed, so there may be an update.”

The decision still open: should option 2 be allowed when you explicitly ask for it, or should every manual brief wait until relevant processing is complete? Allowing it gives you a useful update sooner, with a stated limit. Requiring completion avoids sending an update that might soon be corrected.

The recommendation is to allow that explicit parent-directed exception. It is not approved yet. Merely asking for a brief does not approve sending one with known gaps.

No need to reread everything when saved coverage already supports the requested brief. The ordinary daily brief still requires complete agreed ingestion. Answering a question with stated limitations is already allowed; this open choice concerns sending a manual brief. Nothing is sent by this page.
