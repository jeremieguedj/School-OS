Orientation

What is settled, and what is still open

D1 and the query-coverage rule are approved. You have skipped D2 for now and excluded interrupted-write recovery from the MVP. D3 now requires agents to execute code. Its other choices and D4–D8 remain open. These mechanisms remain unimplemented and unqualified.

Already approved direction and storage

  • Google Drive is the canonical home for processed knowledge, indexes, configuration, work, and history.
  • Raw email and attachments remain in their source systems; temporary copies are discarded after verified persistence.
  • Email identity uses source metadata only. Provider IDs are access aids; content is read separately to extract school information.
  • Work stays bounded and resumable from Drive. Any number of agents and known jobs may participate.
  • Concurrent writes to the same canonical data are outside the present household scope.
  • D1: multiple JSON pages on Drive, with bounded directories and transfers.
  • Answers check coverage as well as saved knowledge, and explain any gap that cannot be resolved within scope.
  • D3: the agent must be able to execute code in its available environment.

Pending architecture mechanisms

  • Minimum record structures and ordinary-write behavior remain undecided; interrupted-write recovery is outside the MVP.
  • Language, code/runtime contracts, and the initial adapter set; code-execution capability is already required.
  • Exact automatic-association threshold and processing budgets.
  • Knowledge/task semantics, briefs, effects, schedules, and upgrades.

Approval boundary. Approving D1–D8 authorizes these architecture choices for implementation. It does not authorize tests, simulations, model runs, connector probes, builds, ingestion, schedules, or live effects. Testing remains a later, user-directed phase.

D1 How should Drive hold the data?

Approved

Approved: use multiple small structured text files (JSON) on Drive, with directories that let an agent find and read a little at a time.

The 64 KiB default is a limit per JSON page; 100 entries is the limit per directory page. Add more pages as history grows. Neither limit caps the whole app. Actual Drive capacity and access costs still need qualification.

Approval scope, alternatives, and unknowns

What approval authorizes

  • A short human-readable bootstrap that names the instance, installed release, logical directories, and how to locate them.
  • One record family per UTF-8 JSON page; at most 100 directory entries per page and a default 64 KiB encoded JSON page limit.
  • Source directories routed by logical mailbox and the UTC month of the original-Date instant, while preserving its original zone and precision.
  • Active-task, knowledge, work, and output directories with explicit continuations. Work stops at the operation budget and persists its next position.
  • Long text split into numbered segments without truncation; startup reads only its narrow bootstrap/configuration/operation/binding/work set.

Alternatives, tradeoffs, unknowns, and dependencies

Credible alternativeNative Google Sheets tables, with a separately bounded representation for long text.
TradeoffJSON keeps nested evidence and unknowns together; Sheets may offer easier bounded reads in some managed connectors. JSON directories add reads and writes.
Key unknownWhether actual target apps can reliably read/write file contents and list folders within these bounds.
DependenciesD2 record shapes, D3 storage adapters, D4 ingestion budgets, D8 package boundaries.

A current Drive URL or ID only helps locate data. Retrieved School-OS instance and role identifiers establish that the correct logical records were reached; duplicates or conflicts remain unresolved.

D2 Deferred: interrupted-write recovery

Outside MVP

Your decision: skip D2 for now. Do not build recovery of interrupted canonical writes for the MVP. The earlier proposal is retained below for future review.

D2 also bundled record fields and ID/locator formats. Those remain undecided; skipping recovery does not remove the need for canonical knowledge, tasks, configuration, and registers.

Approved query rule: check coverage alongside saved knowledge. An unread email might contain exactly what the parent needs. Finish missing processing only within authorized scope and work limits; otherwise make the answer's limitation clear.

For example: “I found these two tasks due tomorrow, but yesterday’s processing is incomplete, so this list may be missing something.” The query rule remains approved despite the recovery deferral.

Retained proposal and approved query rule

Earlier proposal — undecided records; recovery outside MVP

  • Typed families for configuration, email, attachment, knowledge claims, tasks, discovery windows, coverage, work, tools/adapters, jobs, and runs/outputs/effects.
  • School-OS identities generated once and never derived from content or provider IDs; adapter-owned provider locators stay replaceable.
  • A five-stage write procedure: persist and verify intent; apply and read back targets; expose relationships/lookups; mark coverage verified; complete work only after every target is verified.
  • Pending work IDs and verification state travel with changed values. Lost responses are found through known work/family locations and reconciled before another effect.
  • Temporary raw material is discarded only after persistence is verified. Conflicts and incomplete lookups remain explicit.

Alternatives, tradeoffs, unknowns, and dependencies

Credible alternativesImmutable whole-instance generations, or a full event/replay engine.
TradeoffSmall intents make local repair simpler and avoid repackaging all state, but expose more partial states that readers must understand.
Key unknownCross-record recovery and the observed consistency behavior of real Drive adapters.
DependenciesD1 discoverable storage; D3 adapter outcomes; D5 relationship/task semantics; D6 external effects.

No atomicity, lock, lease, conditional-write coordination, generation chain, or content-based identity is assumed.

Approved: answering while work is incomplete

  1. Read verified knowledge and check discovery and content-processing coverage for the source scope needed by the question.
  2. Do not assume unread material is irrelevant because its subject or current saved knowledge shows no match.
  3. Complete missing processing only within existing authorization, capabilities, and budgets; otherwise answer with the gap.
  4. Never claim a complete list, exhaustive count, or absence without supporting coverage. If the coverage lookup itself is unfinished, say so.

A question does not require clearing the entire backlog. This approved query rule does not restore interrupted-write repair or resumption to the MVP.

D3 Must an agent be able to run code?

Yes — approved

Your decision: a School-OS agent must be able to execute code. You have confirmed this capability with the major personal-agent suppliers.

The earlier proposal to support agents without code execution is superseded. A programming language, dependencies, and exact code/adapter contracts still need approval.

Approved requirement and remaining choices

What is approved

  • Code execution is a required agent capability. The supplier confirmation is user-reported; it is not an independently observed School-OS qualification result.
  • This does not require a personal computer, persistent process, or coding CLI, or mean every operation must run code.
  • Agents continue to reason over explicit procedures and use replaceable adapters. No tests or supplier probes are authorized.

What still needs a decision

  • Language/version, libraries, code entry points, and the boundary between code and agent reasoning. Python standard-library helpers remain a proposal.
  • Contracts for storage, source reading, task apps, email delivery, audio, and scheduling, including incomplete capabilities and unknown outcomes.
  • Initial routes: Drive JSON, Gmail, Sheets/Todoist tasks, managed scheduling/runtime profiles, and optional ElevenLabs audio remain proposed.
Earlier alternativeSupport agents entirely through native-tool instructions without requiring code execution. That option is superseded.
TradeoffCode supports repeatable mechanical work, with an execution capability prerequisite. Its exact language and operating limits remain undecided.
Key unknownExact file/network access, libraries, limits, and provider-adapter behavior in each target environment.
DependenciesD1 storage; minimum record/ordinary-write design; remaining D3 contracts; D6 effects; D7 capability records; D8 packages.

Local Codex remains a development surface. A vendor name or reported code capability does not establish that every required adapter operation works. D2 interrupted-write recovery remains outside the MVP.

D4 How should School-OS find and process email?

Pending

D4 contains four choices: enough metadata to identify an email; search windows; processing limits; and reading repeated appearances or attachment candidates.

  1. Identify: require mailbox, subject, sender and the email’s original Date with timezone and seconds before automatic association. If a tool shows only a minute, try a richer metadata view once; otherwise leave the association unresolved.
  2. Search: work through history in seven-day windows; daily runs look back seven days to catch late discovery. Use arrival time for discovery where its meaning is documented, while keeping original sending Date for identity.
  3. Bound the work: propose up to 100 listing entries and 25 message appearances processed per run, with at most 8 MiB per content transfer. Save normal progress and continue later; never infer exhaustion from a short page.
  4. Read separately: matching metadata can reuse an email record, but does not prove the newly encountered content was read. Each admitted appearance is read; same-parent attachments sharing a filename remain a group whose available candidates are processed separately.

Main cost: conservative matching leaves more unresolved items, and the seven-day overlap can cause repeat reading. These defaults remain proposals, not measured capacity or approved D4 policy.

Approval scope, alternatives, and unknowns

What approval authorizes

  • Equivalent zoned original-Date instants agree. Missing timezone, unclear meaning, or minute/day precision stays pending after one available richer metadata read; seconds are never invented.
  • Separate historical and daily half-open discovery windows, preferably using documented received-time listing for arrival discovery. Original Date still controls identity.
  • Defaults of seven-day historical windows, seven-day daily overlap, 25 processed appearances, 100 listing entries, and 8 MiB per content transfer. These are configurable ceilings, not throughput claims.
  • Every continuation page is followed, even after a short page. Lost tokens cause durable window replay.
  • Each admitted appearance is processed independently, even if its metadata reuses a logical email. Same-parent/same-name attachment candidates are all read within the bounded inventory pass when available.
  • Incomplete, unsupported, oversized, unnamed, or ambiguous content remains visible work with precise coverage.

Alternatives, tradeoffs, unknowns, and dependencies

Credible alternativeAdmit agreeing minute-precision Dates, or allow source-grounded agent judgment under an explicit sufficiency table.
TradeoffThe strict threshold produces more pending associations. Processing repeat appearances costs more, but avoids treating unread material as already covered.
Key unknownReal metadata precision, source listing-time semantics, delayed indexing, candidate-read support, and practical transfer limits.
DependenciesD1 pages/budgets; D2 discovery and coverage records; D3 source adapter contract; D5 semantic reconciliation.

Already outside the approved direction: using metadata agreement to inherit prior content coverage, or adding body hashes/provider IDs to avoid processing an admitted appearance. Metadata identity does not prove equal content or that new material was read.

The historical second-resolution evaluator does not prove this threshold universally. Newly imported old mail also needs a supported change route or an explicitly requested rescan; overlap alone cannot promise discovery.

D5 How should school requests and parent edits interact?

Pending

Recommendation: preserve school information with its evidence, turn required actions into tasks, and keep parent plans and completion separate from school deadlines. Compare both sides before accepting conflicting task-app edits.

Approval scope, alternatives, and unknowns

What approval authorizes

  • Claim-level facts keep instructions, conditions, exceptions, dates, applicability, qualifications, provenance, and finite is_action disposition.
  • Corrections, support, and conflicts need evidence-linked relationships. Later dates and repeated wording do not silently overwrite prior claims.
  • Finite requests become canonical tasks. Required recurring actions keep recurrence, applicability, and occurrence/completion history; if native recurrence is unavailable, project explicit occurrences within a default 14-day horizon.
  • Parent owner, planned date, progress, completion, and notes stay separate from school-supported action, context, and deadline. Parent-origin tasks remain visibly parent-originated.
  • Three-way task synchronization compares canonical, remote, and last verified shared values. Divergent edits await review; remote deletion creates a missing projection rather than deleting the canonical task.
  • Replay does not reset a parent’s completion or planned date. Reopening requires explicit parent or source evidence.

Alternatives, tradeoffs, unknowns, and dependencies

Credible alternativesOne-way task export; more compact mutable summaries; another explicit recurrence projection policy.
TradeoffThree-way sync supports parent interaction but adds conflict handling. Claim-level records preserve provenance and correction history but require careful semantic judgment.
Key unknownSemantic extraction quality, provider support for managed identity fields/recurrence, and how much review divergent edits create.
DependenciesD2 claims/tasks/relationships; D3 task adapters; D4 coverage; D6 external-effect recovery.

Title similarity never establishes task identity. Independent developer expectations must be bound to the exact source packet and must separately check action disposition; an empty action set requires source-supported justification. These safeguards do not authorize an audit run.

D6 What belongs in a brief, and when can a send retry?

Pending

Recommendation: select briefs by when knowledge was newly verified or substantively corrected, retain generated audio on Drive until parent deletion, and reconcile uncertain effects before any retry.

Approval scope, alternatives, and unknowns

What approval authorizes

  • Daily/recent updates use the Drive verification/correction interval and display original school dates separately; late-processed historical information is labeled.
  • Briefs include relevant tasks and disclose incomplete ingestion or task-sync failure. A fully read action-free snapshot goes directly to brief composition.
  • Historical import does not automatically send a backlog. Manual recent briefs require an explicit interval.
  • Optional audio narrates the same selected canonical information and is retained as a derived Drive artifact, with inputs and attribution, until the parent explicitly deletes it.
  • Before task writes, schedule changes, email, or audio requests: persist and verify the exact intent, mark outcome unknown, dispatch, then reconcile a complete relevant provider read.
  • Unresolved outcomes remain unknown and stop that effect. Retry requires evidence of non-application, or an explicit parent decision after duplicate risk is explained.

Alternatives, tradeoffs, unknowns, and dependencies

Credible alternativeUse source Date alone for brief recency, or adopt a different explicit audio retention rule.
TradeoffVerification-time selection surfaces newly processed old facts but must label them clearly. Retained audio improves history and attribution but consumes storage and needs parent-led deletion.
Key unknownSearchable provider evidence, eventual visibility, unattended authorization, and the usable form/lifetime of audio artifacts.
DependenciesD2 intents/runs/outputs; D3 effect adapters; D5 knowledge/tasks; D7 scheduler observation.

Already outside the approved direction: blind resend after a timeout, transport failure, or empty search. Unknown writes and sends must be reconciled; a provider receipt alone is not canonical verification.

No procedure promises exactly-once external effects.

D7 How should jobs and their status be tracked?

Pending

Recommendation: record which agent runs each known job, where it is managed, which tools it uses, and when its actual settings were last checked. Keep requested changes separate from confirmed changes.

Approval scope, alternatives, and unknowns

What approval authorizes

  • Capability records use supported/unsupported/unknown states, observed limits, authorization location, and verification time. Declared tools begin discovery; testing them is separately authorized later.
  • Operation defaults and each job’s pinned bindings remain separate. Changing a default does not silently rebind a job.
  • Job creation/change/pause follows D6’s unknown-effect procedure. Desired settings remain pending until externally inspected and recorded.
  • Each scheduled prompt names the Drive bootstrap, operation, scope, budget, bindings, and destinations. Missed jobs recover from durable Drive windows.
  • A fresh reader can explain known jobs, runtimes, management locations, triggers, outputs, recorded generator/sender, and freshness without claiming unseen jobs or live status.

Alternatives, tradeoffs, unknowns, and dependencies

Credible alternativesDifferent register granularity, freshness policy, or job-binding workflow that still preserves multiple agents/jobs and desired-versus-observed state.
TradeoffPer-combination records and pinned jobs cost maintenance, but prevent vendor-name assumptions and accidental rebinding.
Key unknownActual schedule control, readback detail, and unattended permissions for each runtime.
DependenciesD2 tool/job/run records; D3 scheduler contracts; D6 effect recovery; D8 installed operation recipes.

Already outside the approved direction: one fixed scheduler/runtime or a single active-agent slot. The approved product supports the parent’s choice of multiple agents and registered jobs.

D8 How should updates preserve your instance?

Pending

Recommendation: install from a versioned ZIP, keep official files separate from private data and additions, and verify an update before switching to it. Preserve the old project in Git history.

Approval scope, alternatives, and unknowns

What approval authorizes

  • A ZIP containing a manifest, entry point, recipes, versioned record/adapter contracts, defaults, code artifacts subject to remaining D3 decisions, reference mappings, extension guide, and license.
  • Semantic package/contract versions. Meaning or required-field changes need a major version and separately approved migration; additive optional fields may be compatible.
  • Compatible extensions own namespaces and inventories under extensions; upgrades preserve private data, configuration, and extensions.
  • Upgrades stage a new official version, persist intent, check compatibility, verify files, then change the bootstrap pin. The prior package remains available.
  • No implicit migration of retired instances. Fresh-install and “migration not yet authorized” guidance make the boundary explicit.
  • Retire old active runtime/instruction/schema/template/adapter/test trees after the preserved baseline, while keeping principles, restart design, frozen studies, history, continuity, and privacy safeguards.

Alternatives, tradeoffs, unknowns, and dependencies

Credible alternativesIn-place replacement, or migration on every update.
TradeoffStaging and isolated areas cost storage and procedure steps but improve recovery and protect extensions. In-place overwrite is smaller but harder to recover.
Key unknownArchive handling and compatibility behavior in actual managed applications.
DependenciesD1 area boundaries; D2 upgrade intent; D3 packaged recipes/helpers; D7 registered bindings/jobs.

The initial restart remains explicitly unqualified. The optional standard-library archive builder and replacement validation entry point would be prepared during implementation but not run before user-directed testing. Package hashes check official package integrity; they never become source identity.
