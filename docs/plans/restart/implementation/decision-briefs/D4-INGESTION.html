Review status: D4 is pending. This brief explains the current architecture proposal’s D4; it does not approve or implement it. The active plan records approvals. The source-metadata-only identity recipe and product principles remain authoritative. All examples below are wholly fictional written illustrations, not simulations, tests, connector observations, or throughput predictions.

The answer first: yes, a run can end before the task is done

An execution or run is one bounded occasion when an agent works. A scheduled job is an externally managed instruction that may launch executions at its trigger; launching one does not prove its work finished or that another will launch. The logical daily task is to discover and process the relevant arrivals under the configured scope and report its actual coverage. A historical import task may span many date windows and executions. These tasks remain unfinished while their saved windows, admitted appearances, or content work remain pending. Neither “daily” nor “scheduled” means “everything completed in one invocation.”

Within one run there are distinct stages:

  1. Discovery: enumerate the configured source search window through continuation pages and record whether the listing route established exhaustion. A short page is not the end if it has a continuation.
  2. Association: compare allowed source metadata with existing logical emails. One logical record may represent repeated appearances; a search-entry count is not a count of distinct school emails.
  3. Reading and extraction: process admitted appearances and available attachment candidates, extracting substantive information. A metadata match does not imply a new appearance’s content was read.
  4. Persistence and coverage: save source-linked knowledge and the actual discovery/content state on Drive and verify ordinary persistence. Raw material remains at its source; temporary processing copies are discarded after verified saving. The selected minimum ordinary-write mechanism is still undecided.
  5. Brief delivery: a separate application decides which verified information to include and whether/how to send it. D4 does not authorize a brief or establish its timeliness; D6 and D7 are pending.

The approved D1 layout permits further JSON and directory pages without a whole-history cap. D4 proposes planning ceilings per run of 100 listing entries and 25 individual-message processing appearances, plus 8 MiB per content transfer. These unapproved defaults are configurable and lowered when actual runtime limits require it. They are neither measured speed, guaranteed successful reads, a cap on logical records, nor a daily total budget. Ending an execution does not establish that the daily task finished.

Parent-visible implication: a useful result might say, “I found these two verified instructions. Discovery or reading remains unfinished, so this may not be complete.” The approved query-coverage rule permits verified facts with source attribution, but requires coverage before exhaustive lists, counts, or absence claims. It neither requires clearing unrelated pending work nor decides a daily continuation trigger.

Forty admitted appearances: what “25 this run” would mean

Here are three fictional messages within that inventory. The positions are for this illustration only, not permanent identities or an ordering policy:

Appearance in this passFictional email contentIf only the first 25 are read
4“Museum visit: return consent by Friday at noon.”The verified consent task can be reported.
18“Swimming: bring a towel every Wednesday this term.”The verified recurring instruction can be reported.
31“Correction: museum consent is needed Thursday, not Friday.”The agent has not read the correction. It cannot know that Friday is outdated.

This is why a partial brief must say that unread mail may change the answer. A subject line or the absence of a saved correction cannot establish that all deadlines are current.

Imagine a fictional Monday school-mailbox scope. Suppose its listing route has actually followed every continuation, established exhaustion for the declared window, and saved an inventory pass containing exactly 40 admitted individual-message appearances. Suppose every appearance has readable content, and the first run successfully reads and verifies coverage for 25 of them. Under the proposed processing ceiling, it stops with 15 saved appearances pending content work. The agent may accurately report 25 read and 15 admitted appearances unread within that established pass, subject to the actual recorded attachment and content scope. It cannot infer that these are 40 distinct logical emails: two appearances might associate to one logical record, while an uncertain association might remain pending. The remaining 15 might contain a deadline or correction. A truthful brief or query must disclose this limit rather than say Monday’s school information is complete.

Change one condition: the listing route hit its proposed 100-entry ceiling while a continuation remained, or completeness evidence was unknown. Now “15 unread” describes only the known admitted inventory, not all mail in the window. More appearances may exist. If some of the 25 had unread attachments or an unknown inventory, “25 fully processed” is unsupported too. The result should name each stage: “25 appearances read; 15 known appearances remain; discovery continues; attachment coverage is incomplete where recorded.” Counts within a pass are never total source or logical-identity ground truth.

What launches another run for those 15? Not yet decided. The proposal saves content work and orders it before another overlap pass on the same completed interval. It specifies no automatic rescheduling, catch-up count, daily total budget, alert threshold, or latest delivery time. A later job invocation, parent request, or separately approved follow-up workflow could resume work; none is silently authorized by D4’s per-run ceiling.

Three smaller fictional flows

A short page with more results. A school source returns three entries on its first page and a continuation. An agent records that the half-open window is unfinished, follows the next page, then another page if offered. If the listing budget ends before the route states exhaustion, the window stays unfinished on Drive. A parent sees “three found so far; discovery not complete,” not “only three school emails.” Narrowing a window may help reduce work, but a narrow search cannot prove a silently capped tool is complete. Discovery windows use a declared source search-time basis; documented received-time listing is preferred for arrival discovery, whereas each individual email’s original Date governs identity. A provider internal or observation time cannot quietly be renamed received time.

A lost temporary token. A fictional agent reaches page two, saves an unfinished window, and loses its pagination token. A fresh agent repeats the window and uses allowed metadata to reuse supported logical-email records, without the old token or chat. It follows continuations through the seen prefix to new work under its listing budget. If the prefix consumes that budget, the proposal narrows the unfinished time window where possible or records a no-progress limitation for review. It neither spins on the same prefix nor claims exhaustion from narrowing. This ordinary saved-window continuation remains in MVP scope. Skipped D2 excludes interrupted canonical-write discovery and repair; this example promises no repair of partially saved canonical writes.

One large attachment. A fictional field-trip email has a 10 MiB named attachment. D4’s proposed 8 MiB is a ceiling for one content transfer, not a declaration that attachments above it disappear or that total history stops at 8 MiB. A supported bounded/segmented reading route might process it under actual capability; otherwise the attachment is recorded oversized, unread, or unsupported with its scope and next action, and the already verified email facts stay usable. The proposal does not promise that every adapter can segment this attachment. A parent asking “What does the trip form require?” gets verified email information plus the explicit unread-form limitation, not a guessed answer or a complete-form claim.

Repeated appearances are not free processing

Imagine a newsletter discovered Friday and appearing again during seven-day daily overlap. Verified mailbox, subject, sender, and original Date may justify one logical-email record. D4 still recommends processing each admitted appearance independently and reconciling extracted knowledge semantically. Friday’s metadata match does not prove Monday’s content or attachments were read. This costs repeat reads under overlap and replay. The proposal saves inventory-pass assignments before content work, then finishes pending content before a new overlap pass on that interval. This limits accidental loops without proving a universal cost bound. Pass IDs track assignments, not permanent provider-entry identities.

Historical windows and daily overlap both default to seven days. The two progress tracks remain separate; missed windows catch up under available bounds. Newly imported older mail may evade the overlap and need a supported change route or explicit historical rescan. Search counts and provider-entry differences prove neither distinct logical emails nor total substantive information.

Why have a limit, and could it be higher?

Managed executions have finite time, context, memory and tool capacity. A chosen ceiling is a planning allowance: leave room to save and verify progress instead of admitting more content until the environment stops. It is not proof that an unexpected interruption cannot happen. D2 repair is still excluded.

The proposed 25/100/8 MiB values have not been measured or qualified. They are conservative draft starting values, not evidence that 25 is the right number for a household. They can be revised explicitly. A higher processing allowance can finish more in one run but consumes more runtime capacity; a lower allowance stops sooner and requires more continuation. A transfer limit affects whether particular large content is readable, not merely how many emails fit.

There is no fixed total-history limit from these numbers. There can still be a throughput problem: if new work plus overlap rereading exceeds what the authorized runs can process, pending work grows. Scheduling more runs, raising allowances or changing the rereading strategy would need concrete design review. Saving a backlog is not evidence that it will eventually clear.

Exact original Date: a pending threshold, not a proven law

The approved identity recipe preserves each individual email’s original sending Date, meaning, timezone, and precision; a reply has its own Date and coverage. Received time may help comparison or discovery, but never silently replaces original Date for identity. D4 must decide how much evidence is sufficient for automatic reuse or new-record creation. Its recommendation requires verified logical mailbox, original subject, normalized sender, and original Date with a known timezone and declared second-or-finer precision, with no comparable contradiction and a complete relevant lookup. Equivalent zoned instants compare equally. A search result with unclear time gets one available richer individual-metadata read. If only minute/day precision, missing timezone, or uncertain time meaning remains, association stays pending. Seconds and timezone are not invented.

For a fictional reply whose search listing says “Tuesday 09:12,” the individual header might reveal “Tuesday 09:12:37 −0700.” Under the recommendation, that exact source Date can participate in association. If the richer view still supplies only “09:12,” the agent keeps candidates pending and continues unrelated work; it cannot use the provider’s received timestamp or the reply’s thread starter to fill the gap. Another minute-precision email could be indistinguishable under permitted metadata. Even second precision does not guarantee physical uniqueness. The historical second-resolution evaluator and fictional fixture domain did not establish a universally sufficient production threshold.

A credible alternative admits agreeing minute-precision Dates or source-grounded agent judgment, with an explicit sufficiency table. It may reduce pending work but increase incorrect joins. A strict threshold increases review and cannot remove residual indistinguishability. New-record creation also needs a completed lookup showing no compatible existing record; missing optional fields alone cannot create one. Provider IDs, bodies, hashes, attachment bytes, and thread IDs cannot resolve ambiguity under the approved boundary.

Same filename, same parent: a group, not a shortcut

Suppose the fictional field-trip email presents two attachments both originally named trip.pdf. D4 recommends a same-parent candidate group and reading all available candidates within the current bounded inventory pass. If one is a permission form and the other a transport note, source-linked extracted facts can initially say they came from the group, with exact attachment attribution marked uncertain. Different retrieval handles or listing positions do not prove two distinct documents; identical names do not prove one document or equal content. A later reordered inventory cannot inherit a prior candidate’s processed status by ordinal, handle, or filename. The same name in a different parent email is a separate lookup context.

If only one candidate is readable, the coverage record states that one was read and the other was unread/unsupported within the actual inventory scope. If the source did not establish a complete original-name inventory, even “both attachments accounted for” is unsafe. An unnamed inline image or oversized candidate remains explicit work. Content structure is useful for extraction, but cannot settle email/attachment identity or inferred thread association. This is the reason a search entry can be logically associated while its content coverage remains incomplete.

The approval choice and what is still missing

Approving D4 as written would select the exact zoned original-Date automatic threshold; separate historical/daily half-open discovery tracks and search-time semantics; configurable seven-day windows/overlap and 100-listing/25-appearance/8-MiB planning ceilings; follow-all-pages and token-loss window replay; saved inventory/content-pass ordering and processing of admitted appearances; and same-parent candidate-group coverage. It would not approve D2 interrupted-write repair, undecided record/ordinary-write structure, remaining D3 adapter details, D6 brief delivery, D7 scheduler control, or any test. The full proposal is the authoritative scope; reply with explicit approval or named revisions and record the decision in the active plan.

Suggested direction for review, explicitly unapproved: keep D4’s honest bounded continuation; let a separately approved D7 job binding determine whether/when another execution resumes saved work; let D6 explicitly label any partial brief and its coverage, with a parent-configured freshness target and aggregate catch-up budget. This offers a visible parent outcome without pretending a single run finishes everything. A complete-before-delivery rule favors certainty but could delay useful verified news; a qualified-by-time rule favors timeliness but must expose missing content prominently. Neither policy, scheduler trigger, aggregate limit, nor alert is contained in the current D4 approval request. They require concrete proposals and explicit user approval before implementation.

Metadata precision, listing exhaustion, delayed indexing, attachment reading, runtime limits, cumulative cost, unattended continuation, and brief timing remain unqualified. Architecture approval authorizes its stated mechanisms only. Tests, simulations, builds, connector probes, ingestion, schedules, and live runs await user direction after code publication and remote verification.
