Q10 · one unresolved implementation decision

Keep oversized values lossless and bounded

The approved design requires numbered pieces but never defined how fresh agents store and follow them. This page presents the exact proposed representation. It does not adopt it.

Nothing on this page is implemented as approved architecture. Q1 reserves segment_refs, and D1 requires lossless numbered pieces, but neither defines their record or reference shape. Until Q10 is decided, a write that needs segmentation remains blocked.

Where the missing shape matters

The gap affects three already-approved values: a Knowledge statement, Knowledge relationships, and Task parent_state.completion_reviews. Small values keep their current shape. No other field gains segmentation by implication.

Recommendation: one narrow segment family

Use one record_segment family. Each segment has a School-OS ID, its owning Knowledge or Task, the field being split, a one-based ordinal, a chunk of JSON-encoded text, and an optional next reference. The owner stores only the first reference and expected count.

Segments use ordinary bounded D1 JSON pages and the same family-directory/locator mechanism as other canonical records. They are access machinery, not new facts, emails or Tasks. This adds no generic writer, queue, service, garbage collector or repair engine.

The exact proposed shape

A long Knowledge statement replaces statement with the already-approved segment_refs field:

{
  "value_encoding": "json_text",
  "first_ref": {"family": "record_segment", "id": "segment_<uuid-v4>"},
  "segment_count": 2
}

An oversized relationships or parent_state.completion_reviews array becomes {"state":"segmented","segment_refs": <the same descriptor>}. This is a known alternative representation, not an empty or unknown array.

Each segment, inside the normal D1 page envelope, is:

{
  "segment_id": "segment_<uuid-v4>",
  "owner_ref": {"family": "knowledge", "id": "knowledge_<uuid-v4>"},
  "field_path": "statement",
  "ordinal": 1,
  "text_chunk": "first part of the JSON-encoded value",
  "next_ref": {"family": "record_segment", "id": "segment_<another-uuid-v4>"}
}

The final segment omits next_ref. IDs are assigned once and never derived from content. Task completion-review segments use a Task owner reference.

Write, switch, reconstruct, verify

1 · EncodeEncode the whole original field as JSON text.
2 · SplitSplit losslessly at character boundaries, preferring paragraphs.
3 · SaveWrite and read back a complete new immutable chain.
4 · SwitchChange and read back the owner descriptor and required indexes.
5 · ReadFollow, verify, join and decode every expected piece.

Each containing page, including escaping and envelope overhead, stays within 64 KiB. Every logical value change creates a complete chain with new segment IDs. The current referenced chain is never edited in place before the owner switches.

A reader verifies owner, field, ordinal, distinct IDs, next links and the exact segment count. It concatenates all chunks and decodes JSON once into the original string or array type. A missing piece, cycle, duplicate ordinal, wrong owner, wrong type or unexpected continuation is incomplete data. It never becomes a shortened fact or history.

The owner revision changes with the logical value. Derived indexes use the reconstructed whole value. Whole-email ingestion cannot complete until every required piece is saved and checked.

What this buys, and what it costs

Benefits: lossless retained knowledge, bounded pages and references, fresh-agent interoperability, and no provider-derived identity or new dependency.

Costs: extra Drive reads and writes only for oversized values. Changing a value copies its chain. Old unreachable pieces may remain and consume storage because automatic cleanup is not proposed. Individual JSON-text chunks are inconvenient to read alone; only the complete reconstructed value has the original meaning.

Save/readback remains non-atomic under the existing MVP boundary. The proposal adds no interrupted-write recovery promise, checksum identity or automatic cleanup guarantee. Actual connector cost and reliability remain unknown until later authorized trials.

Credible alternatives

  • Separate segment families for each field. Individual pieces are more self-describing, but School-OS gains three parallel formats and more adapter/documentation work.
  • Raise the page limit or allow oversized records. This reduces reads, but changes approved D1 bounds and may fail on managed-agent transfer limits.
  • Block oversized values in the MVP. This avoids a new shape, but cannot meet the approved lossless information/history requirement and leaves affected ingestion incomplete.

The exact decision boundary

Explicit user approval would adopt only this segment record, descriptor, allowed fields and lifecycle. It would not qualify the implementation, restore D2 recovery or the generic writer, authorize a different schema, or authorize an unrelated test sequence.

The next phase remains: decide Q10, finish the retained MVP, commit and push it, verify the exact remote revision, then run the three already-authorized isolated seven-day ingestion trials. No trial has started.
