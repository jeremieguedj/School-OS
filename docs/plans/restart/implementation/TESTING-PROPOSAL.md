# Restart testing proposal

Status: **PREPARED — NOT RUN.** This is a proposed test inventory for the user
to direct after the agreed implementation publication checkpoint. No test,
simulation, model replay, smoke run, build, connector probe, ingestion, scheduled
job or live qualification was executed to prepare these artifacts. Publication
hygiene is separate from functional testing and supplies no behavior evidence.

The [restart plan](../PLAN.md#decision-authority-and-user-checkpoints) governs
approval and the stop before testing. The [product principles](../../../product-principles.md)
and [metadata recipe](../identity/METADATA-RECIPE.md) govern expected behavior.
The [historical lifecycle simulation](../SIMULATION.md) supplies useful scenarios,
but its provider/part identity, persistence and harness mechanisms are not the
restart specification. The [frozen metadata study](../identity/metadata-stress/README.md)
and its [protocol](../identity/metadata-stress/PROTOCOL.md) remain unchanged.

## Prepared material and its limits

[Fictional scenarios](fixtures/scenarios.json) contain 12 fictional source cards
and 29 scenarios with independently authored
logical labels, metadata observations, short source-content surrogates,
substantive expectations and lifecycle events. All people, institutions,
mailboxes, messages, outputs, agents and schedules are fictional. These are
scenario descriptions, not canonical schemas, adapter response formats,
installation manifests or a proposed runtime dependency. The invented labels
are test references; an implementation assigns its own School-OS record IDs.

The source cards and expectations were authored before any implementation output
was available. They were not generated by, copied from or checked against a
runtime. A future blind extraction trial must give the interpreting agent only
source material and the authorized operation instructions, hiding expected
facts, actions, logical labels and scenario explanations. An independent grader
uses the separately retained expectations. This single preparation file is a
convenient inventory, not a claim that a blind trial or independent review has
already happened.

The fictional text surrogates do not stand in for real PDF, visual, table, audio
or attachment parsing evidence. No attachment bytes, hashes, provider receipt
shapes, actual deployment costs or production-sized datasets are supplied.
Executable harnesses and native fixture artifacts must be prepared against the
approved implementation when the relevant contracts are settled. Do not copy
the retired runtime to fill those gaps. Required code and instructions for the
whole project remain in implementation scope even when their qualification is
scheduled later.

Before an authorized semantic trial, bind each independent expectation to the
exact test packet and its ordered content segments using the applicable
developer evidence discipline. No packet binding or hash has been computed here.
These bindings prove test-input integrity; they must never become source-email,
attachment or thread identity evidence. A zero-Fact expectation is substantive:
the future trial must reject its reuse for another packet, including a packet
that contains a finite action requirement. Audit the final assembled knowledge
and action inventory against source-bound expectations as well as checking
individual packets.

## Grading rules

- Use independent fictional logical labels to distinguish known repeat
  observations from known different logical emails. Do not use access-handle
  counts as the expected canonical-email count. Where all permitted metadata is
  indistinguishable, report the policy outcome and residual information limit
  separately; do not demand an unavailable distinction or invent a content
  fallback. The live study established neither distinct logical emails nor
  information loss for its matching pair.
- Grade source association, enumeration, body processing, attachment-candidate
  processing, canonical persistence, task reconciliation and output status
  independently. Catalog presence or a successful association cannot make
  unread content complete. A daily success cannot close an old historical gap.
- Assess substantive information at the level of facts, applicability,
  qualifications, explicit corrections, deadlines and action disposition, with
  provenance. A fact count or copied expected answer alone is insufficient.
  Preserve the earlier claim when a later source explicitly corrects it; do not
  infer an unapproved universal latest-timestamp-wins rule.
- Grade a query by the evidence and parent state it actually reads, its answer,
  its source links and the limits it discloses. Source deletion cannot erase
  accepted knowledge or authorize invented missing details.
- Inspect every relevant durable write and readback in authorized recovery
  trials. A source-index readback does not prove that knowledge, tasks, coverage
  and unfinished work were persisted. A lost response or generic error does not
  establish provider success, failure, throttling or safe retry.
- Keep implementation coverage, fictional test results, observed connector
  conformance and managed-agent qualification separate. Passing one of these
  never implies the others. No fixture assumes a vendor supports a capability
  solely from its name.

## Proposed sequence for the user to direct

Only stages within the user's subsequent testing direction may proceed;
completing a stage does not expand that authorization. The user chooses the
scope, environment, revision and timing and may authorize several stages at once.
Before any execution, confirm which architecture decisions have been explicitly
approved and identify how the chosen deliverables realize them. Unapproved
mechanisms cannot be selected through a test harness or pilot.

1. **Review the published implementation and proposed oracles.** Select the
   exact published revision, the scenario subset and the allowed execution
   surface. Review the source cards independently of implementation output.
   Set user-approved budgets and stop conditions. Resolve any contract gaps
   before producing fixtures in their native formats.
2. **Direct the fictional metadata and procedure cases.** Exercise S03–S11 and
   S18 with no private sources or external effects. Include reordered catalog
   candidates, repeated observations, missing/changing handles, explicit empty
   versus unknown fields, source Date semantics, a later reply and short pages.
   Report distinguishable results separately from the S05 information limit.
3. **Direct substantive extraction and canonical recovery.** Exercise S12–S17,
   S22–S23 and S26–S29 on wholly fictional material. Include actual visual/table
   artifacts when authorized, budget interruptions before/after each relevant
   durable write, mismatched readback, and properly input-bound independent
   expectations. Inspect assembled action flags and zero-action progression.
4. **Direct one bounded managed-agent/Drive journey.** Use the approved layout
   and contracts to install a fictional instance, enumerate a small historical
   window, process a daily reply and preserve an unread attachment gap. Verify
   bounded reads, actual persistence and temporary-copy cleanup. Measure the
   observed work, not declared fixture sizes. No private migration is implied.
5. **Direct external task, email and optional audio cases.** Select services and
   authorized test destinations explicitly. Exercise parent completion,
   planning dates, source corrections, recurring requirements with exceptions,
   provider-equivalent empty readback and
   unknown-write reconciliation before any retry. Then inspect actual brief
   content, recency, delivery evidence, audio support and attribution.
6. **Direct scheduling and fresh-agent replacement.** Create only the selected
   fictional test schedules when specifically authorized. Inspect desired and
   observed settings, a missed invocation and the actual scheduler location.
   Start a fresh capable second agent with only the Drive entry point; query
   school information and known jobs, resume the unfinished window without its
   token, and process a later reply. Run sequentially; concurrent same-data
   writes are outside scope.
7. **Direct upgrades and measured expansion.** Exercise a supplied update while
   preserving fictional private data, configuration and a compatible custom
   application/adapter. Expose incompatibilities without overwriting the old
   instance. Repeat targeted capability checks for additional selected adapters
   and workloads only as directed. Keep remaining unqualified areas explicit.

## Approval dependencies and remaining unknowns

The exact Drive file/table layout, canonical schemas and record relationships,
persistence/recovery behavior, adapter contracts, runtime dependencies,
scheduling design and upgrade compatibility mechanism need the approval status
recorded in the active plan. These scenarios do not decide them. In particular:

- Date precision, partial recipient and attachment inventory observations are
  supplied without inventing a generalized acceptance policy beyond the current
  recipe. Unsupported or insufficient evidence must remain scoped and pending.
- Unknown external task, schedule and delivery outcomes require an approved
  reconciliation procedure. These scenarios prohibit claiming success or
  blindly retrying, but do not specify an unapproved effect engine.
- Cross-mailbox task equivalence and ambiguous school corrections require an
  approved semantic reconciliation procedure. The prepared correction cases
  contain explicit statements; they do not authorize inference by recency alone.
- A recurring school requirement remains action-relevant even when it has no
  one-time response deadline. Preserve recurrence, applicability and exceptions;
  the approved task contract must decide its representation and advancement.
  An advisory guideline does not supply the same obligation. Do not classify
  all standing requirements as non-actionable.
- Native attachment reading, complete enumeration, exact provider empty-value
  equivalence, actual permissions and operational cost require real evidence
  in an authorized phase. Fictional observations cannot qualify connectors.
- Failure-evidence storage must honor the existing developer privacy boundary
  without making local receipts a parent-instance recovery dependency. Any new
  mechanism still requires architectural approval.

At the completed whole-project implementation publication checkpoint, report
these artifacts as prepared, all tests as not run, and the exact next action as
awaiting the user's testing direction. Until the implementation and publication
conditions are met, record the actual next action instead: the current
architecture checkpoint awaits explicit architecture approval for dependent
implementation. If architecture or publication is blocked, report that blocker
separately; neither condition authorizes execution.
